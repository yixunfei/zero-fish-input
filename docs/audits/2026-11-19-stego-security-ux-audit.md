## 2. 安全类遗留

### S8（信息）测试覆盖缺口

**现状**：本轮修复补了字节边界、门控预警与续期、凭据显示/清空、粘贴代次与全局开关等回归。二次回源更正：门控断言并不缺失，仍待完成的是平台拒绝矩阵：

- **系统剪贴板的真实拒绝矩阵**：URI、`Intent`、多条目、仅 `text/html`、锁屏等拒绝路径仍主要依赖代码审查与部分平台用例；`docs/text-steganography-validation.md` 记录该矩阵在最近一次运行中被保守跳过。
- **`begin()` 预算断言已存在**：`StegoCarrierTest` 顶部的 `operation near editing expiry has a fresh bounded working window` 已覆盖第 119 秒开始、越过原编辑截止后完成、工作超时及过期编辑拒绝。本次再加强新预算恰为 120000 毫秒、119999 毫秒有效、120000 毫秒失效的精确断言。此前只检查文件后段得出缺失结论，属于漏读。

**后续**：在具备可控公开样本所有权的隔离设备补齐系统剪贴板拒绝矩阵，不放宽既有预检查换取通过。

## 3. 体验类遗留

### U1（高）密钥文件往返丢失已输入的待解密文本

**状态**：未修复。提醒已改准确，但行为未变。

**证据**
- `StegoWorkspace.kt:367-369`：`KEY_FILE` 动作仍然是 `dialogs.confirm(stego_file_warning) { close(); onSource(StegoAction.KEY_FILE) }`，`close()` 清除全部草稿。
- `ZeroInputService.kt` 的 `Kind.FILE` 请求不携带载文；返回时 `open(..., carrier = null, file)`。
- 文案 `stego_file_warning` 现明确“会清除全部草稿……请先选择文件，返回后重新导入载文”，`stego_file_missing` 同样引导。

**影响**：解密一条密钥文件消息的自然流程仍是“粘贴载文 → 发现需要文件 → 点密钥文件 → 选择 → 返回后载文消失 → 重新粘贴”。独立密文还要重填精确 cover。提醒变准确降低了困惑，但没有降低工作量，该模式在长文本下依然接近不可用。

**建议**：这是已确认的产品取舍，不改数据流也可以进一步降低摩擦——在解密模式进入时就把“先选择密钥文件”做成前置步骤（此时草稿为空，清除无代价），而不是让用户先输入再被清除。若要彻底解决，需要把已验证载文随 `Kind.FILE` 传给私有宿主（载文是密文 + 公开 cover，与现有 `VAULT_COVER` 传递独立密文的边界一致），并在 ADR 0039 补一句授权。

### U3（高）随机共享密钥没有可用的分发路径

**状态**：未修复。仅新增降级提示。

**证据**
- `StegoWorkspace.kt:262-288`：`generateKey()` 生成后只写入凭据字段。
- `StegoWorkspace.kt:429`：`saveField()` 明确拒绝 `CREDENTIAL` 与 `KEY_BITS`。
- 无复制按钮、无系统剪贴板写入、无 SAF 导出；`stego_random_key_help` 说明“目前只能手动转录……跨设备优先使用口令或密钥文件”。

**影响**：256 位密钥是 43 个 Base64url 字符，4096 位是 683 个字符。接收方只能手抄或逐字键入，几乎必然出错。该凭据模式实际上只适合同设备或极短密钥。

**建议**：短期维持现状即可（提示已经足够明确）。若要做，优先“生成密钥文件并通过 SAF 另存”的显式导出（设计文档已列为未来特性，需要单独 ADR 评估导出面），不要用系统剪贴板。二维码方案需评估截图风险，不建议在无 ADR 时实现。

### U2（中）凭据字段无粘贴、无光标、强制掩码

**状态**：部分修复。输入帮助与清空已补，能力缺口仍在。

**证据**
- `StegoWorkspace.kt:142`：每次输入都把 `reveal` 置回 `false`，字段在输入过程中始终掩码。
- `StegoWorkspace.kt:243-248`：`pasteTargetAllowed` 对 `CREDENTIAL`、`KEY_BITS` 返回 `false`，这两个字段没有粘贴路径。
- `StegoWorkspace.kt:130-161`：凭据分支只处理 `Text`、`LiteralText`、`PairedText`、`Space`、`Backspace`，没有 `MoveDraftCaret` 分支。
- 文案 `stego_credential_input_help` 现明确“英文直接输入……不支持粘贴或光标移动，可清空重输”。

**影响**：字段本就使用英文布局（首轮“拼音被逐字符当密码”的判断有误，已更正），所以不存在中文被吞。真实缺口是三处：12 位以上口令只能逐字键入且无法粘贴；输错只能从末尾删除；输入过程中不能核对，只能停下后主动显示。

**范围澄清**：凭据粘贴受明确禁止，不能作为普通 UX 优化自行加入。当前保留手动输入、主动显示和确认清空；改变显示方式或输入能力需另行评估，文案继续说明限制。

### U6（中）预览后“重新编辑”需重输秘密正文

**状态**：部分修复。已加确认与说明，未从结果恢复正文。

**证据**
- `StegoWorkspace.kt:326-328`：`EDIT` 现在先 `dialogs.confirm(stego_edit_warning)`，文案说明结果、秘密、凭据与文件因子将被清除。
- `StegoWorkspace.kt:538`：`publish()` 成功后仍 `drafts[StegoField.SECRET]?.clear()`。
- `StegoWorkspace.kt:627-630`：`clearPrepared()` 关闭并清零 `outputs` 中的明文。

**影响**：预览发现公开文本有错别字，点“重新编辑”后必须重新输入整段秘密正文；对 2 KB 正文是灾难性的。确认框至少避免了误触，但没有降低代价。

**建议**：这属于“结果即焚”的取舍。若不想保留秘密正文，可考虑允许从 `outputs` 的明文副本回填到隔离草稿（掩码、生命周期受控、随 `close()` 清零），代价是多一份短暂明文副本；若维持现状，保持确认文案即可。

### U19（中）旋转丢弃私有宿主与草稿

**状态**：未修复（按设计不保存秘密）。

**证据**
- `app/src/main/AndroidManifest.xml:181-185`：`StegoSourceActivity` 未声明 `configChanges`，与其他 Activity 的配置不同。
- `StegoSourceActivity.kt:80`：`onCreate` 设置 120 秒预算；重建后不再持有原请求。

**影响**：在选择文件或查看条目列表时旋转屏幕，Activity 重建，草稿与流程丢失。安全上这是保守的（不把秘密写进 `Bundle`），但用户看到的是页面突然消失。

**建议**：不要为了旋转把秘密写进实例状态。可做的补偿是重建后给出明确说明（“旋转屏幕会清除隐写草稿”），或在进入私有宿主时提示“请勿旋转屏幕”。前者需要区分“重建”与“首次创建”，实现成本低。

### U7（低）私密空间条目没有类别标签

**状态**：部分修复。已显示更新时间，仍无类别。

**证据**
- `StegoSourceActivity.kt:209`：条目文案为 `stego_entry_time`，显示“条目 N · 时间”。
- `StegoSourceActivity.kt:276`：保存时仍 `vault.add("", ...)`，标签为空。
- `SecureClipboardVault.summaries()` 的 `displayName` 固定为空。

**影响**：四种输出（明文 / 公开文本 / 密文 / 完整载文）保存后完全不可辨，用户只能靠时间和顺序猜。

**建议**：认证后读取标签再显示（当前索引不读标签是合理的边界）。如果连认证后也不想显示，至少在保存成功后用 Toast 说明“已保存为完整载文”，让用户记住刚才存的是哪一种。

## 4. 二次回源结论

### R1：拒绝提交保护应保留，直接输入的恢复体验需要统一

候选转换拒绝时，`PendingEngineCommit` 保留用户尚未确认放弃的输入。此时只凭已接受前缀仍在预算内就允许提交，会静默丢弃输入意图，不采用原建议。既有回归已覆盖重复提交仍拒绝、首次退格只撤销待确认候选；撤销后可直接提交原有合法正文，无须再删一个字符。

新增复现进一步发现：直接字符、成对符号及无组合换行的拒绝路径没有 pending engine update，原先第一次退格会删除已有正文。现统一为第一次退格撤销拒绝状态、保留正文，第二次开始正常删除；键盘动作和命令入口一致。超限提示明确说明未加入和撤销方法。候选拒绝并非本轮新增缺陷，不能将全部拒绝保护判作“修复引入”。

### R2：成立，已修复

组合转换耗尽有界完成步骤后仍可能未结束，而未触发长度拒绝。原统一长度提示不准确。现 `LocalDraftInput.submissionBlockReason` 只暴露阻塞原因；`StegoWorkspace.submittedField` 供加解密、下一项和保存共同使用，分别提示预算拒绝或组合未完成。没有增加正文副本或自动截断/提交前缀。

### R3：报告中的跨进程抢占推断未证实

Android 16 AOSP 的 `IInputMethodSessionWrapper.updateSelection` 通过 `HandlerCaller.executeOrSendMessage` 处理；非主线程回调排入 IME 主线程。正常跨进程通知不会抢占当前主线程上 `target(text); close()` 的连续调用。源码见 [IInputMethodSessionWrapper](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/core/java/android/inputmethodservice/IInputMethodSessionWrapper.java) 与 [HandlerCaller](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/core/java/com/android/internal/os/HandlerCaller.java)。主线程同进程直接调用可以同步分派，但当前报告没有这类复现，不能把假设标为已确认竞态。

保留消费令牌后单次插入及真实选区变化立即撤销，不增加“忽略下一次回调”。先关闭再插入也会使现有目标的面板资格校验失败，并非仅影响失败提示。特殊 OEM 或自定义同步重入尚未独立验证。
